# AI-DLC on Antigravity

This project uses AI-DLC (AI-Driven Development Life Cycle) for structured development, running on the **Antigravity harness** (the Antigravity IDE and the Antigravity CLI `agy` share this install). The workspace shell ships in `.agents/` (no setup command); describe what you want to build and it sets up the workflow for you. Run `/aidlc` followed by a scope or project description to begin. Run `/aidlc --doctor` to validate your setup, `/aidlc --version` to print the framework version, `/aidlc --stage <slug>` to jump to a specific stage, `/aidlc --phase <name>` to jump to a phase, `/aidlc --depth <level>` to override depth, `/aidlc --test-strategy <level>` to override test volume, `/aidlc --review <class>` to cap stage reviews (adversarial, advisory, none). Antigravity-native shortcuts expose `/aidlc-status`, `/aidlc-jump --stage <slug>` (or `--phase <name>`), and `/aidlc-scope <name>` through the same workflow. Run `/aidlc compose "<task>"` to get a plan tailored to that task (works up front, from a scan report via `--report <path>`, and mid-workflow to re-shape the pending stages - every proposal stops at an approve/edit/reject gate).

## Prerequisites

- **Antigravity**: the Antigravity IDE or the Antigravity CLI (invoked as `agy`). Both read this install's `.agents/` surfaces (rules, skills, agents, hooks). Verified against agy cli-2026.10 — hooks (`.agents/hooks.json`) and skills (`.agents/skills/`) are current-line features.
- **A trusted folder**: Antigravity loads a workspace's `.agents/hooks.json` once the folder is trusted, and without the hooks your approvals are never recorded. Trust the folder when Antigravity asks (or add it to `trustedWorkspaces` in your Antigravity settings), then send your next message in the same chat.
- **bun**: Required for the CLI tools and hook scripts (tracking progress, writing the decision log, deciding what runs next). Install via `curl -fsSL https://bun.sh/install | bash`. `bun` must be on your PATH for the shells Antigravity spawns.
- **Permissions**: every shell command, including AI-DLC's own engine calls, follows your Antigravity permission settings; choose "always allow" for the `bun .agents/tools/aidlc.ts` commands the first time they ask so the forwarding loop is not interrupted by a prompt per engine call. Headless `agy -p` runs cannot answer a permission prompt and run their commands in a sandbox, so they suit the read-only utilities (`--status`, `--doctor`, `--version`) only; gated workflows need an interactive session regardless, because an approval gate waits for the person's own message.
- **Locking**: Audit log file locking is handled portably using mkdir-based locking in the system temp directory (no external dependencies).
- **Hook permissions**: All 17 hooks are TypeScript (`.ts`) and run via `bun`. No executable bits required — works identically on macOS, Linux, and native Windows PowerShell.

## AI-DLC Structure

- **Skill**: `.agents/skills/aidlc/` — Orchestrator (`SKILL.md`), stage protocol, and the stage files across the phase directories (the enabled set depends on the composed plugins: see the compiled `.agents/tools/data/stage-graph.json` or run `bun .agents/tools/aidlc.ts --doctor`)
- **Document skill** (user-invocable): `.agents/skills/aidlc-knowledge/`, typed as `/aidlc-knowledge`; the framework CLI also exposes `bun .agents/tools/aidlc.ts engine knowledge <verb>`. Also standalone — outside the lifecycle graph — but classified `read-write`, unlike the read-only session skills below: it changes the document catalog and emits document audit events. It never advances the workflow stage pointer and never approves a gate. See "Document knowledge" under "Where things live" in the project's root `AGENTS.md` (Claude Code and Copilot readers find it under "Shared AI-DLC onboarding" in this file).
- **Session skills** (read-only, user-invocable): `.agents/skills/aidlc-session-cost/`, `.agents/skills/aidlc-replay/`, `.agents/skills/aidlc-outcomes-pack/` — typed as `/aidlc-session-cost`, `/aidlc-replay`, `/aidlc-outcomes-pack`. Each pulls every count from `bun .agents/tools/aidlc.ts engine runtime summary --json` (no LLM-side counting). Classified `read-only`: they never advance the workflow stage pointer and never emit audit events. `aidlc-session-cost` and `aidlc-replay` print to the terminal only; `aidlc-outcomes-pack` is the only one that writes a file (`OUTCOMES.md`).
- **Stage-runner skills** (user-invocable): `.agents/skills/aidlc-<stage>/`: one per runnable core stage, typed as `/aidlc-<stage>` (e.g. `/aidlc-domain-design`, `/aidlc-code-generation`); plugin-owned stages use their bare plugin-prefixed command name. Each runs that single stage in isolation via the engine's `--single` mode (`aidlc-orchestrate next --stage <slug> --single`) and **never advances your main workflow's `Current Stage`**: `next --single` records only the synthetic start boundary and `report --single` closes that same attempt. They are opt-in packaging: the same stage is reachable via `/aidlc --stage <slug> --single` without a runner. The runner set is generated from the compiled stage graph by `bun .agents/tools/aidlc.ts engine gen runners` and kept in sync by its `check` drift guard, so adding a stage file and regenerating adds its runner. The three bootstrap **initialization** stages ship no per-stage runner (they have no standalone meaning); the whole initialization phase is packaged as `/aidlc-init`: with `--scope <name>` and a description it creates the workflow record and its starting state in one step, with `--scope <name>` and nothing else it first asks what the work is for, and with only a description it first shows the same plan offer as describing the work. (This is opt-in packaging: describing what to build normally sets up the first piece of work by itself; no separate initialization command is needed.)
- **Agents**: `.agents/agents/` — the base framework ships 14 agents: 11 domain-expert personas (product, design, delivery, architect, aws-platform, compliance, devsecops, developer, quality, pipeline-deploy, operations), 2 review-only agents (product-lead, architecture-reviewer), and the adaptive-workflows composer. A plugin install may add more; the enabled set is discovered from the files present under that directory. On Antigravity each expert role is a native subagent (discovered from the persona files in `.agents/agents/`); the `/aidlc` session takes on those roles itself for most stages and hands work off via the `invoke_subagent` tool for the two delegated stages (2.1, 3.5). They ship without `model:` pins — every agent inherits your session model.
- **Sensors**: `.agents/sensors/`: automatic checks that run on matching writes or once per existing deliverable at the approval gate. Gate-fired sensors may be advisory or blocking; blocking failures require an explicit audited override before the gate opens. Ships with framework defaults (`aidlc-claim-sources.md`, `aidlc-required-sections.md`, `aidlc-upstream-coverage.md`, `aidlc-traceability.md`, `aidlc-linter.md`, `aidlc-type-check.md`); forks may add custom `aidlc-<id>.md` manifests. Stages declare which sensors fire via the frontmatter `sensors: [<id>]` list — a pull import resolved at compile time.
- **Knowledge**: `.agents/knowledge/` — Methodology reference. Per-agent under `aidlc-<agent>-agent/` subfolders; `aidlc-shared/` holds cross-agent material. Ships with framework.
- **Tools**: `.agents/tools/`: small command-line programs (TypeScript, run via bun) that do the parts which must be exact rather than judged: tracking where the workflow is, writing the decision log, deciding what runs next (`aidlc-orchestrate.ts`, with exactly six subcommands: `next`, `continue`, `report`, `park`, `team-board`, and `wait`; `continue` is internal steering transport and `team-board` is the read-only Team Construction query, and `wait` is the bounded read-only wait for dispatched work), running the automatic checks, recording what the team learned (`aidlc-learnings.ts`), and refereeing parallel Construction work (`aidlc-swarm.ts`). All framework files prefixed `aidlc-*.ts`.
- **Hooks**: `.agents/hooks/`: scripts your CLI runs automatically at set moments, so the decision log, saved progress, and status display stay correct without anyone remembering to update them. All framework files prefixed `aidlc-*.ts`.

## Plugins

AI-DLC is open-world. Plugins under `plugins/<name>/` contribute additional stages, scopes, and agents, and `select-plugins` chooses which are enabled in this install. The counts above describe the base framework; your enabled set may differ. The compiled `.agents/tools/data/stage-graph.json` and `bun .agents/tools/aidlc.ts --doctor` are the authoritative live view of what is enabled here.

## Guards

The guards are the person's checks. When the person asks in their own words to turn one of their checks off or back on, or to change the Guard Policy ("turn the review freeze check off for this project", "stop asking me to re-approve when files change", "relax the change checks", "turn it back on"), do it for them in the same turn and say the line the command prints, word for word, in your reply in that same turn, before any question, picker or next step (the command's output alone does not reach them): never refuse, never ask them to type it, and never investigate first. Asking for the guards or the checks as a whole to be off ("turn the guards off") is Guard Policy `off`, even when the same message also names one check. "Stop asking me to re-approve when files change" is Guard Policy `relaxed`, not one check; when Guard Policy is already `off`, say in one line that it is already off and change nothing. Turning a check on, or Guard Policy `strict`, is always fine; turning one off, or Guard Policy `relaxed` or `off`, happens only when they ask, never on your own and never as a suggestion. Where it applies is what they say: this piece of work, this project, or this machine. When they say neither, use this piece of work while one is open, otherwise this project; the line names where it applied. When the line ends with a question offering a wider place, that question is the only one: it is asked by saying the line, or by one picker carrying the same question instead, never both, and when they say yes, set it there yourself with the command from the table; a line that ends with no question asks nothing. For this piece of work run `bun .agents/tools/aidlc.ts engine config set <key> <on|off> --person-words '<their words>'` with the key from the table. For this project run `bun .agents/tools/aidlc.ts config flags --bypass <switch> --local --yes` (`--global` for this machine). To turn it back on, `bun .agents/tools/aidlc.ts config flags --clear-bypass <switch> --yes` clears it everywhere it is recorded, so the check is really on; when they name a place, add `--local` or `--global` to clear only there. A `none` in the table means that place has no switch for the check: when they named no place, use the place it has; when they named a place it does not have, say in one sentence that it cannot be set there and offer the other place, and change it only when they agree. Guard Policy is set for a piece of work only; with none open, say so in one line. For Guard Policy run `bun .agents/tools/aidlc.ts engine config set guard-policy <strict|relaxed|off> --person-words '<their words>'`; when the team holds Guard Policy strict in memory, it refuses with one line naming the file, and you say that line. A typed `/aidlc --guard-policy off` or `/aidlc config set guard.<fence> off` was applied when the message arrived. Never edit `aidlc-state.md` or run a hook to change a guard. `/aidlc --status` shows the current Guard Policy and every fence with where its setting came from. A remark about being careful with changes, or a question about a check, is not a request to change it; when you cannot tell, ask once.

## Models and effort

When someone asks in plain words to change an agent's model or effort ("make the developer agent think harder"), run `bun .agents/tools/aidlc.ts config models --agent <name> --effort <low|medium|high|xhigh|max> --project --yes`. For a model, use `--model <id>` in place of `--effort`, or both when they ask for both. Use `--local` instead of `--project` when it is only for them. If it asks for `--harness`, run it again naming this tool's harness. Print its output and stop. Never edit the `aidlc-*-agent` files for this.

## What's different on this harness

This is the same AI-DLC core that ships to every harness: the same ordered steps, the same approval gates, and the same written record of what was decided, rendered onto Antigravity. On Antigravity:

- Approval gates and questions render through the native **`ask_question` modal** (the questions FILE with `[Answer]:` tags remains the source of truth).
- Hooks ride `.agents/hooks.json` through the AIDLC adapter (`.agents/hooks/aidlc-antigravity-adapter.ts`): state-transition, reviewer read-scope, review-freeze, and plan-approval guards block via Antigravity's `decision: deny` channel before tools; audit and sensors cover file writes and edits; stage-graph rebuilds run after shell commands; the human-turn record is written when a message of yours starts a turn.
- The forwarding-loop enforcement (the Stop hook) is **live**: Antigravity's Stop hook can send the agent back into the loop while a directive is pending.
- There is **no session-end event and no pre-compaction event** on this host: a session's end is not recorded, and state validation runs with the engine's own checks instead of before compaction.
- The AI-DLC method (`aidlc/spaces/<space>/memory/*.md`) reaches context through read instructions because Antigravity rules do not expand `@`-imports: `.agents/rules/aidlc.md` always points to org/team/project, while four model-decided `.agents/rules/aidlc-phase-*.md` files point to phase guidance only when relevant. The SessionStart hook separately injects live workflow state; `/aidlc space <name>` re-points all five rules in place.
- Subagent identity on hook payloads is **reconstructed by the adapter** from each conversation's own transcript and the `invoke_subagent` dispatch record: reviewer read-scope enforcement keys on that ledger.
- There is **no statusline** and **no welcome message**; use `/aidlc-status` (or `/aidlc --status`) and the progress lines at gates.
- Construction swarm runs as **`invoke_subagent` fan-out only** (`AIDLC_USE_SWARM=1` is a loud no-op).
- **Codex CLI and Antigravity cannot share a project**: both discover skills in `.agents/skills/`.
- **MCP servers**: none ship (configure your own in Antigravity's MCP settings if needed).
- A workflow's `aidlc/` workspace tree is harness-neutral: a project can move between harness installs (supported but untested — keep the trees in sync via the framework's packaging if you do this).

The Antigravity-specific guide (install, what differs, verification) is `docs/guide/harnesses/antigravity.md`.
